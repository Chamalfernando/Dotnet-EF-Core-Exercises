# Users CRUD API — Implementation Notes

This document records **exactly** what was added to implement a CRUD API for
`User` using **EF Core + LINQ**, running against **PostgreSQL** now and designed
to switch to **SQL Server** later with a config change. It also covers the
containerization changes.

- **Project:** EFCoreExcercises (ASP.NET Core 8 Web API, controller-based)
- **Target framework:** net8.0
- **Current database:** PostgreSQL (provider is config-driven — see §6)
- **Verified:** full CRUD cycle was run against PostgreSQL in Docker (see §9)

---

## 1. Packages added

EF Core 8 packages were pinned to `8.0.11` to match `net8.0` (the machine has
SDK 10, whose default EF packages/tooling target net10 and are incompatible).

```bash
dotnet add package Npgsql.EntityFrameworkCore.PostgreSQL --version 8.0.11
dotnet add package Microsoft.EntityFrameworkCore.SqlServer --version 8.0.11
dotnet add package Microsoft.EntityFrameworkCore.Design --version 8.0.11
```

- **Npgsql.EntityFrameworkCore.PostgreSQL** — PostgreSQL provider (used now).
- **Microsoft.EntityFrameworkCore.SqlServer** — SQL Server provider (for the
  future switch; installed up front so switching is config-only).
- **Microsoft.EntityFrameworkCore.Design** — required by the `dotnet ef` tooling
  for migrations.

`Swashbuckle.AspNetCore` (Swagger) was already present.

Run it via `dotnet tool run dotnet-ef ...` (or `dotnet dotnet-ef ...`).

## 4. The entity and DbContext

`Models/User.cs` — fields: `Id`, `FirstName`, `LastName`, `Email`,
`CreatedAt`, `UpdatedAt?`. Validation attributes mirror the DB constraints.

`Data/AppDbContext.cs` — exposes `DbSet<User> Users` and configures a
**unique index on `Email`** in `OnModelCreating`.

---

## 5. Service layer (EF Core + LINQ)

`Services/UserService.cs` uses LINQ over `DbSet<User>`:

- `GetAllAsync` / `GetByIdAsync` — `AsNoTracking()` read queries that
  **project directly into `UserDto`** in SQL (`.Select(u => new UserDto(...))`).
- `CreateAsync` / `UpdateAsync` / `DeleteAsync` — tracked writes via
  `SaveChangesAsync`.
- `EmailExistsAsync` — `AnyAsync(...)` used by the controller to return `409`
  on duplicate emails.

Emails are normalized (trim + lowercase) before save/compare.

Registered in `Program.cs` with **scoped** lifetime (correct for anything that
uses a DbContext):

```csharp
builder.Services.AddScoped<IUserService, UserService>();
```

## 6. Provider selection (PostgreSQL now → SQL Server later)

The provider is chosen at runtime from the **`DatabaseProvider`** config key, so
switching databases needs **no code change**. In `Program.cs`:

```csharp
var provider = builder.Configuration.GetValue<string>("DatabaseProvider") ?? "Postgres";
var connectionString = builder.Configuration.GetConnectionString(provider)
    ?? throw new InvalidOperationException($"No connection string for '{provider}'.");

builder.Services.AddDbContext<AppDbContext>(options =>
{
    switch (provider.ToLowerInvariant())
    {
        case "sqlserver":            options.UseSqlServer(connectionString); break;
        case "postgres":
        case "postgresql":           options.UseNpgsql(connectionString);    break;
        default: throw new InvalidOperationException($"Unsupported provider '{provider}'.");
    }
});
```

`appsettings.json` holds both connection strings and the active provider:

```json
"DatabaseProvider": "Postgres",
"ConnectionStrings": {
  "Postgres":  "Host=localhost;Port=5432;Database=efcoreexcercises;Username=postgres;Password=postgres",
  "SqlServer": "Server=localhost,1433;Database=efcoreexcercises;User Id=sa;Password=Your_password123;TrustServerCertificate=True"
}
```

> Connection strings here are for **local dev only**. For real secrets use
> `dotnet user-secrets` or environment variables (see §8).

## 7. Migrations

The initial migration was generated for the **active provider (PostgreSQL)**:

```bash
dotnet tool run dotnet-ef migrations add InitialCreate --output-dir Migrations
```

This produced PostgreSQL-specific schema (`timestamp with time zone`,
identity columns) under `Migrations/`.

Applying migrations: the app calls `db.Database.Migrate()` on startup
(`Program.cs`), so the schema is created/updated automatically when it runs
(local or container). To apply manually instead:

```bash
dotnet tool run dotnet-ef database update
```

## 8. Containerization changes

### Dockerfile / project (from the earlier Linux conversion)
- Base images switched to Linux: `mcr.microsoft.com/dotnet/aspnet:8.0` and
  `sdk:8.0`.
- `<DockerDefaultTargetOS>Linux</DockerDefaultTargetOS>` in the `.csproj`.
- Build args use `$BUILD_CONFIGURATION` (Linux shell), not `%...%`.

### New: `docker-compose.yml`
Runs the API together with PostgreSQL:

- **`db`** — `postgres:16`, with a `pg_isready` **healthcheck** and a named
  volume `pgdata` for persistence.
- **`app`** — built from the `Dockerfile`, `depends_on` the db with
  `condition: service_healthy` so it waits for the database.
- The DB host inside the compose network is the **service name `db`**, not
  `localhost`. This is injected via an env var that overrides appsettings:

  ```yaml
  ConnectionStrings__Postgres: "Host=db;Port=5432;Database=efcoreexcercises;Username=postgres;Password=postgres"
  DatabaseProvider: "Postgres"
  ASPNETCORE_HTTP_PORTS: "8080"
  ```
- Only HTTP `8080` is published (no dev HTTPS cert inside the container).

Run it:

```bash
docker compose up -d --build      # build + start app and db
docker compose logs -f app        # watch app logs
docker compose down               # stop (keep data)
docker compose down -v            # stop and delete the db volume
```

Swagger: <http://localhost:8080/swagger>

## 10. How to switch to SQL Server later

The code does not change — only configuration and migrations:

1. **Point config at SQL Server:**
   - Set `"DatabaseProvider": "SqlServer"` in `appsettings.json`
     (or env var `DatabaseProvider=SqlServer`).
   - Ensure `ConnectionStrings:SqlServer` is correct.

2. **Regenerate migrations** (provider-specific column types differ between
   PostgreSQL and SQL Server, so the existing `Migrations/` cannot be reused
   as-is):

   ```bash
   # remove the PostgreSQL migrations
   #   (delete the Migrations/ folder, or: dotnet tool run dotnet-ef migrations remove)
   dotnet tool run dotnet-ef migrations add InitialCreate --output-dir Migrations
   dotnet tool run dotnet-ef database update
   ```

3. **Containers:** add a SQL Server service to `docker-compose.yml`
   (`mcr.microsoft.com/mssql/server:2022-latest`, `ACCEPT_EULA=Y`, `SA_PASSWORD`)
   and point `ConnectionStrings__SqlServer` at host `db` (e.g.
   `Server=db,1433;Database=efcoreexcercises;User Id=sa;Password=...;TrustServerCertificate=True`),
   plus set `DatabaseProvider: "SqlServer"` on the `app` service.

> **Advanced (keep both providers simultaneously):** maintain separate
> migration folders per provider (e.g. `Migrations/Postgres`,
> `Migrations/SqlServer`) using `MigrationsAssembly`/`--output-dir` and select
> the set at design time. Not needed for the current single-target setup.

## 12. Debugging in Visual Studio with Docker Compose (Option A)

### Why this was needed
The **"Container (Dockerfile)"** green-button profile launches **only the app
container**. With no database in that launch, the app's `Host=localhost` resolves
to the app container itself, so Npgsql fails with:

```
Npgsql.NpgsqlException: Failed to connect to 127.0.0.1:5432
```

The fix is to debug with **Docker Compose**, which starts the app **and**
PostgreSQL together and lets the app reach the DB at `Host=db`.

### What was wired up
A Docker Compose **orchestration project** was added so the green button runs
both containers (with full breakpoint debugging):

1. **`docker-compose.yml`** (base) — restructured to VS conventions:
   - `db` service: `postgres:16` + healthcheck + `pgdata` volume.
   - `efcoreexcercises` service: built from `Dockerfile`, named after the
     project so VS maps it to the project and injects the debugger. It
     `depends_on` the db being `service_healthy`.

2. **`docker-compose.override.yml`** (dev settings, auto-merged by VS and by the
   `docker compose` CLI):
   - publishes ports `8080:8080` (app) and `5432:5432` (db),
   - sets `ASPNETCORE_ENVIRONMENT`, `DatabaseProvider`, and the container
     connection string `ConnectionStrings__Postgres=Host=db;...`.

3. **`docker-compose.dcproj`** — the VS orchestration project
   (`Sdk="Microsoft.Docker.Sdk"`, `DockerTargetOS=Linux`). It sets the launch
   browser URL to `/swagger` and `DockerServiceName=efcoreexcercises`.

4. **`EFCoreExcercises.sln`** — registered the `docker-compose` project
   (project type GUID `{E53339B2-1760-4266-BCC7-CA923CBCF16C}`) with Debug/Release
   configurations.

### How to use it in Visual Studio
1. **Reopen the solution** (or click *Reload* if VS prompts that the .sln
   changed). A **docker-compose** project appears in Solution Explorer.
2. If the green button does not already say **"Docker Compose"**, right-click the
   **docker-compose** project → **Set as Startup Project**.
3. Press the green **Docker Compose** button. VS builds the image, starts
   `db` (waits until healthy) and `efcoreexcercises`, applies the migration on
   startup, and opens **<http://localhost:8080/swagger>**.

> First run pulls `postgres:16` and the .NET base images, so allow a little time.

### Notes / gotchas
- If VS shows *"the project file cannot be opened"* for `docker-compose.dcproj`,
  the **Container development tools** workload (which provides
  `Microsoft.Docker.Sdk`) is missing — install it via the Visual Studio
  Installer. As a fallback, you can regenerate this project from the IDE:
  right-click the API project → **Add → Container Orchestrator Support → Docker
  Compose → Linux**, then re-merge the `db` service.
- The old **"Container (Dockerfile)"** profile still exists but should not be used
  for running the app, since it has no database.
- The CLI path is unchanged: `docker compose up -d --build` still works
  (it merges `docker-compose.yml` + `docker-compose.override.yml` automatically).
